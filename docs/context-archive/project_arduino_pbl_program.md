**What this is.** A research-grounded curriculum of **8 differentiated Arduino PBL projects** for 7th–12th grade EBD students at Agourim School, designed to maximize independent work so a solo teacher can rotate to students needing more support. The final product doubles as a curriculum guide AND a proposal to the Israeli Ministry of Education requesting budget and support.

**Why:** The existing work in this repo (framework, research summaries, one LEGO project) distilled principles; this program is the concrete operationalization — actual projects, built on verified research, with a Ministry-ready academic package wrapped around them.

**Major design decision locked 2026-04-11 (Phase D planning, before Phase D execution): CLAUDE CODE IS A DUAL-CHANNEL SUPPORT.** Principle 7 was expanded from a single-channel "three-level coding support" model to a **two-channel** model. **Channel A** is the existing pair-programmer role with three levels (Level 1 upload / Level 2 modify-with-AI / Level 3 free dialogue). **Channel B** is a new **scaffolded tutorial channel** where a student invokes Claude Code with "I'm on Project N, Tier X, task card M — walk me through it" and Claude responds conversationally, breaking the card into small steps and asking checkpoint questions. **Channel B is available at any tier including Tier 1** because the receptive conversational format ("read me what to do") is cognitively simpler than Channel A Level 3's productive format ("help me debug my code"). Channel B addresses reading-load / instruction-parsing barriers, which Channel A does not. **Both channels sit alongside the printed task card — neither replaces it.** The student still holds the physical card and still checks off milestones on it; Channel B is a parallel delivery mode for students who benefit from conversational delivery. Every project in Phase D ships with a **Claude Code tutorial-channel scaffold** (short system prompt + per-milestone invocation templates). **Evidence status:** Channel B has even less direct support than Channel A (which was already the program's weakest-supported principle). §9 Honest Limitations explicitly flags both channels as piloted practices with no direct empirical precedent, and both the master document's §4 Principle 7 and `Arduino_Principles.md` canonical Principle 7 acknowledge this openly. **Implications for Phase D artifact production:** every project's artifact family now includes a "Claude Code tutorial-channel scaffold" document in addition to the existing task cards, pre-written .ino files, HTML tutorial, reference cards, and checklists. This expands the per-project artifact inventory (documented in the plan file at `~/.claude/plans/sorted-purring-starlight.md`).

**Major design decision locked 2026-04-11 (Phase C §5 drafting): EVERY PROJECT IS DESIGNED FOR INDIVIDUAL STUDENT WORK.** Peer collaboration / pair work / small-group work / role-based cooperation is **NOT a first-class mechanism** in the current version of the program. Every student works on their own project, at their own workstation, at their own tier, at their own pace. The workshop is a small-group physical setting (3–8 students in the same room sharing parts library and tools) but the work is individual. Rationale: (a) extra coordination complications would overwhelm a single teacher rotating to 3–8 students, (b) social dynamics are already a load for this population with many carrying histories of social difficulty, (c) individual projects preserve the three-tier and three-level-Claude-Code differentiation models cleanly, (d) Wattanawongwan 2021's cooperative-learning research requires teaching and monitoring five specific elements which is itself a first-class instructional commitment the program has chosen not to make, (e) Gomez 2019's peer-interaction mechanism is honestly not being implemented. **Decision is deferral, not rejection** — conditions for revisiting are documented in Appendix A of `Arduino_PBL_Program.md`: one full implementation year of data, case-by-case student requests, staffing changes, or a dedicated Project 9 shared-build unit. **Implications for Phase D project design:** every project file (Arduino_Project_1.md through Arduino_Project_8.md) must be designed as a single-student project. Role vocabulary (Driver/Navigator/Documentarian/Peacekeeper) is preserved in Appendix A for future use but does NOT appear in §5 Methodology or the project files. Principle 8 has been rewritten to "**The teacher–student relationship is the multiplier**" — adult mentoring, not peer collaboration, is the relational mechanism the program commits to. This change propagated across `Arduino_PBL_Program.md` (§1, §4 P5, §4 P8, §5 section list, §5.1, §5.7 deleted and renumbered to §5.9, Appendix A added) and `Arduino_Principles.md` (canonical Principle 8). **Additional Phase D cross-project design decisions locked 2026-04-11 (session 3):**

12. **Complete printed cards, not thin scaffolds.** Yon's explicit design directive: *"the printed cards should include everything so they will provide a second method of presenting the tasks to the students."* Every Tier 1, Tier 2, and Tier 3 task card across all 8 projects contains everything the student needs for that milestone — wiring diagram, code snippet, Claude Code prompt, expected result, "done when" criterion, "stuck" protocol — except the subset that genuinely cannot be printed (the click Upload action, the live Claude Code conversation, running the code). A student with a printed card in hand can read everything they need except the actual computer operations. This replaced the original plan of thin cards + a separate richer HTML tutorial. Thin cards were too reference-heavy for this population; complete cards give students who prefer paper a genuinely paper-complete path.

13. **Printed cards and HTML tutorial share a visual template.** Yon's directive: *"the look of the printed cards should be as similar to the look of the html ones so that one could easily switch between them."* Both use the same CSS style, same colours, same typography, same section patterns. A student can put a printed card next to the HTML tutorial page and immediately see they are the same content in two formats. This is implemented via a shared `task_cards/style.css` file that all 14 task cards link to, and the HTML tutorial (Chunk 4, not yet drafted) will link to the same stylesheet.

14. **HTML tutorial must have clickable links, not plain text URLs.** Yon's directive: *"please make sure that all links will be clickable because typing urls by hand or even copy and paste may sometimes be too much for some of the students."* Every file path in the HTML tutorial is a clickable relative-path `<a href="ino_files/...">` link that, when clicked, opens the `.ino` file in the Arduino IDE (assuming Windows has Arduino IDE set as the default for `.ino` files). Every external URL is a full `<a href="https://...">` link. No URL is shown as plain text for the student to type or copy-paste. Tutorial includes a one-time instruction block at the top: *"First time using the tutorial? If Windows asks how to open a sketch, pick Arduino IDE and check 'always use this app.'"*

15. **Task card format: A4 portrait at 14pt body text.** Confirmed 2026-04-11 session 3. Driven by two factors: (a) complete printed cards need more room than A5 allows (wiring diagram + code snippet + expected result + done-when + stuck protocol all fit comfortably on A4, tight on A5); (b) 14pt body text is within the dyslexia-friendly range (14-16pt recommended) and matches the readability needs of the EBD/ADHD student population. Reference cards R1-R5 also at A4 14pt for workflow consistency — the teacher prints and laminates one page size, not two. The original Chunk 2 at A5 12pt was rebuilt in session 3 after Yon asked whether A5 was readable enough and confirmed A4 for the task cards.

16. **Shared CSS file approach for task_cards/.** The 14 task cards all link to a single `task_cards/style.css` file instead of each having its own `<style>` block. Dramatically smaller HTML files, easier style iteration (one file to tweak), and the shared CSS file travels with the directory when the teacher copies it to student Drive folders. Workflow: browser renders the HTML with the linked stylesheet, print from browser. This is a deliberate departure from the self-contained approach used for reference cards R1-R5 (which each have their own embedded `<style>` block) — task cards are a cohesive set that share a template, reference cards are standalone references that don't need to match each other exactly.

Three layers of revision at three timescales: **within-session** (teacher verbally adjusts for the student in front of them, not recorded), **weekly** (teacher uses the weekly data collector to note patterns and applies revisions to the local workshop copy before the next week's sessions), and **between-cohort** (end-of-semester reflection + weekly digests → revised master document and per-project files, tracked in git). 9. **Per-student Google Drive folder architecture** — cross-project infrastructure decision for all 8 projects.    - **One shared Google account** for the whole robotics workshop. All students, all workshop PCs, and Yon share this one account. Per-student isolation is by subfolder naming convention under `G:\My Drive\Arduino_Projects\`, NOT by separate accounts.
   - **Google Drive for Desktop** installed on every Windows 11 workshop PC, logged in under the shared account, mounting the account's My Drive as `G:\My Drive\` (a local Windows directory Claude Code can operate on).
   - **Claude Code** is launched at each workstation **pointed at the student's current project folder** rather than as a generic browser tab. Claude can read the student's actual `.ino` files and iterate on them in place — this qualitatively improves Channel A Level 2/3 and Channel B.
   - **Persistent workspace across sessions.** A student who spent Session 1 wiring returns to Session 2 with their sketches, modifications, photos, and notes exactly where they left off. By end of year, each student has 8 project folders — a tangible portfolio of "things I built" that supports §7.1 Cluster 1 (the super-target).

The privacy architecture is that students pick their own nickname at their first workshop session, and that nickname (not their real name) appears in the folder path. The privacy concern is identity protection from anyone who might see the folder structure (other students, visitors, future cohorts, IT, parents), not access control.
